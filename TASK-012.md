# TASK-012: Session-based task locking to prevent agent conflicts

## Goal

Prevent two implementer agents from simultaneously working on the same task by adding session-aware locking to `taskforge start`, `done`, and `block`, with a new `unlock` command for manual recovery.

## Background

The session ID is a 10-char hex string (5 bytes from `crypto.randomBytes`) generated by `start` and embedded directly into the branch name. The branch name format becomes:

```
agent/TASK-012-a1b2c3d4f5
               ^^^^^^^^^^ -- session GUID
```

The agent reads its identity from the branch name via `git rev-parse`. No extra files or environment variables needed.

Lock flow:
- `start` checks `lockedBy` in frontmatter → if set and different from own session → reject
- `start` generates GUID, sets `lockedBy`/`lockedAt` in frontmatter, creates branch with GUID in name
- Agent commands (`done`, `block`) assert ownership by comparing branch GUID to `lockedBy`
- `done`/`block` clear `lockedBy`/`lockedAt`
- `unlock --force` clears locks manually (human recovery)

## Expected Output / Behavior

- `taskforge start TASK-012` → generates GUID, creates branch `agent/TASK-012-<guid>`, sets `lockedBy`/`lockedAt` in frontmatter
- `taskforge start TASK-012` again (same worktree) → OK (re-entrant, GUID matches)
- `taskforge start TASK-012` (different clone) → rejected: "Task is locked by session <guid>"
- `taskforge start TASK-012 --force` → clears stale lock, re-locks
- `taskforge done TASK-012` → clears lock, marks Done
- `taskforge unlock TASK-012 --force` → clears lock without status change
