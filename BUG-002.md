# BUG-002: `taskforge next` Recommends Tasks Already Merged to Main

## Observed Behavior

`taskforge next` recommended TASK-034 (status: In Progress, P1) as the highest-priority task, even though that task's implementation was already merged into main. The task file's status field had not been updated to Done because the previous agent merged via raw `git merge` without calling `taskforge done`.

## Expected Behavior

`taskforge next` should not recommend tasks whose feature branches are already merged into main. It should either:
- Auto-transition such tasks to Done (since the code is merged), or
- Skip them and log a warning

## Root Cause

The previous agent merged the feature branch to main using raw git, bypassing the `taskforge done` lifecycle. The task file status remained `In Progress`. `taskforge next` relies solely on the `status` frontmatter field and has no awareness of git branch merge state.

## Acceptance Criteria

- [ ] `taskforge next` checks whether a task's feature branch commits are ancestors of `main` before recommending
- [ ] If merged: auto-completes task (status → Done, clears lock, appends note) and skips it
- [ ] `taskforge start` also checks and refuses to start a task whose branch is already merged
- [ ] `taskforge doctor` reports any In Progress tasks whose branches are merged to main (inconsistency)
- [ ] Check uses `git merge-base --is-ancestor` or `git branch --merged` — cheap local operation
- [ ] Works even if the feature branch was already deleted (check commit ancestry, not branch existence)
- [ ] All existing tests pass
- [ ] Tests cover: merged branch detection, deleted branch detection, non-merged branch passes through

## Guardrail Principle

Agents must not be able to circumvent the task lifecycle via raw git operations. The system must detect when task state and git state diverge and self-correct.
